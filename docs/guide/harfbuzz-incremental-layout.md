# HarfBuzz 增量排版

> 当前增量实现见[原生段落增量布局](./native-incremental-layout.md)。
> 下文是早期实现记录；旧行恢复算法和引擎选择已在 T20 删除。

## 配置与重排边界

```typescript
{
  lab: { incrementalCompute: true }
}
```

HarfBuzz 的增量单位是段落，复用单位是未变段落的行与字形。
一次编辑可能改变同段阿语连写、BiDi 顺序和后续断行，不能从任意旧行快照续算。
因此完整重排受影响段落，其他段落不再进行文本桥接、整形或行映射。

插入/删除使后续元素下标变化时，同步移动行起始索引、元素来源索引、cluster 索引、
字形逻辑索引及光标导航布局。字形的段内字符偏移和视觉位置保持不变。
复制需要改索引的布局，避免修改整形缓存。旧的绝对段落索引句柄会被清理。

## 适用范围

- 正文纯文本、上下标、混合 LTR/RTL、段落间距和自动换行。
- 受影响段落从编辑点前一元素扩展到完整段落边界，支持拆段、合段和跨段删除。
- 分页与元素坐标仍完整计算，确保后续页面位置跟随行高变化。
- 通过既有脏区间追踪接入真实输入、键盘删除及插入 API。

以下情况回退完整排版：

- 文档含列表、控件、表格、图片、标签、区域或其他非纯文本结构。
- 分栏、浮动/环绕元素，以及上次发生 maxPageNo 截断。
- 没有可靠脏区间、文档列表替换、样式或配置变化、引擎显式失效。
- 段落边界对象身份与缓存无法对齐。

原地修改字段必须使用 `draw.setElementProperty` / `draw.deleteElementProperty`，
增删元素必须使用既有增删入口；直接修改元素会绕开脏区间追踪。

单个超长段落仍需重排整段。当前实现没有复用分页坐标，也不保证一帧内完成整次编辑。
legacy 引擎继续使用原有行级续算路径，两种引擎不共享恢复快照。

## 验证与测量

专项测试使用真实 Noto Naskh Arabic 字体及 HarfBuzz 整形，与关闭增量的独立编辑器
比较行、字形、分页与完整坐标，并检查后续段落的光标导航布局。
覆盖连续插入/删除、拆段/合段、跨段删除、空段落、上下标、真实键盘输入、
撤销重做、样式/缩放/缓存失效，以及复杂布局回退。

30 段文档的局部编辑测试确认只调用一次段落布局，未变前缀保留原行对象，
后续段落移动逻辑索引后与全量排版一致。

ESLint、TypeScript 检查与应用构建通过；全量回归在 `--maxWorkers=4` 下
通过 122 个测试文件、725 项测试。默认并发运行曾触发一项既有 legacy 超长段落
差分测试的 30 秒超时，降低并发后该测试通过。未执行浏览器 Cypress 验证。

2026-10-16 本机 jsdom 测量：120 段、9,988 个元素，在中部连续插入 7 次，
每次只重新扫描 84–90 个元素。排版及坐标计算的编辑耗时中位数为：

| 路径 | 中位耗时 |
| --- | ---: |
| 全量 | 248.9 ms |
| 段落增量 | 15.3 ms |

该测量使用已加载字体，关闭历史记录提交并启用懒绘制，不含真实 Canvas 绘制。
这是测试环境中的单次测量，不能视为浏览器实际帧率或所有文档的性能保证。
